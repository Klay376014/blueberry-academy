# ADR-0012：歸屬永遠等於「拿現在的別名清單重跑一次推導」的結果

- 狀態：Accepted
- 日期：2026-08-28
- 相關：#64、#67、#69、#70、CONTEXT.md「身分」

## 脈絡

一場對戰是誰的 —— `my_side` 與隨之派生的 `my_username`、`opponent_username`、
`result`、兩條 signature、`bring_complete`、`rating`、`rating_delta` —— 原本只在匯入
路徑上算過一次，寫死進資料列。

這在「先綁名字、再匯入」的順序下沒有問題。反過來就卡死：使用者先匯入了 replay，
名字還沒綁，整批落成旁觀場次；接著去設定頁綁上名字 —— 什麼都不會發生。既有的資料列
不會被碰，首頁的名字下拉甚至生不出那個名字（那份選單是從已載入的資料列推出來的），
整頁重整也沒用，因為要重整的不是畫面而是資料。

而 `CONTEXT.md` 已經寫明：**系統無法驗證 Showdown 帳號的擁有權**，綁定是純粹的信任
模式。無法驗證，就表示綁錯名字（包括把對手的名字綁進去）不是罕見情形，而是這個設計
必然會發生的事。歸屬一旦寫死，綁錯就成為一個**使用者沒有任何介面能修復的狀態**。

## 決定

**`battles` 各歸屬欄位的值，永遠等於「拿現在的別名清單、對該場的兩側資料重跑一次
歸屬推導」的結果。**

由此推出的幾件事：

- 推導是一個純函式，住在 `battle-row` 套件（`attributionOf`）。匯入路徑與事後的重新
  歸戶走同一份，不可能給出不同答案 —— 那正是這個套件存在的理由。
- 重跑**只讀 `details`**，不讀 Storage、不重新解析、不打 Showdown：兩側的完整解析
  結果與 winner 本來就都存在那裡。
- 綁定、解綁、以及設定頁上常駐的「重新歸戶」按鈕，都是同一條回填路徑的呼叫端。
- 綁定時要對該使用者**全部**的資料列重跑，不只目前沒有歸屬的那些。既有規則是「兩位
  玩家都綁在同一個帳號時 p1 優先」，所以某場已歸給 p2 的場次，在使用者之後綁上 p1
  那位的名字時應該翻正；只掃沒歸屬的列會再次留下一個無從修復的狀態。
- 旁觀不是一場對戰的永久屬性，只是它此刻的歸屬狀態。

回填的形狀（分批、只寫有變動的列、中途失敗停下不回滾）是這個決定的配套，理由記在
#67 的 commit 與 PR 裡，不重複。

## 後果

**好的：** 使用者的操作順序不再重要 —— 先匯入或先綁名字都會收斂到同一個結果。綁錯
名字有解（解綁），而解綁與再綁定是可逆的來回，有測試整列比對釘住。「重新歸戶」也順帶
成為別名清單在另一台裝置被改動後的同步入口。

**代價一：寫回不能重用整列 upsert。** `regulation` 是 generated column
（`supabase/migrations/20260820070352_data_floor.sql:36`：
`regulation text generated always as (…) stored`），Postgres 不接受對它的寫入，所以
讀回整列再寫出去會被資料庫拒絕。歸屬因此有一個**只涵蓋那九個欄位的窄寫入方法**
（`setAttribution`），欄位清單與其他每一份一樣留在 `apps/web/app/shared/api/battles.ts`。

> 這一條是從 schema 推出來的，不是量到的：這個決定沒有真的送一次整列 upsert 去看
> 錯誤訊息。若哪天有人想「順手」改回整列寫入，請先實測。

**代價二：一次綁定是一次全表掃描。** 重度使用者按一次綁定就是讀幾千列、算幾千次。
可接受的理由是推導很便宜（純函式、只讀 `details`），而且**只有真的有變動的列會被
寫入** —— 絕大多數列重算結果與現況相同，所以第二次跑是零寫入。

**代價三：歸屬欄位的值不再是「匯入當下的事實」的紀錄。** 若未來想回答「這場在三月時
算誰的」，資料庫答不出來。目前沒有任何功能需要這個問題的答案。

## 替代方案

- **歸屬在匯入當下一次寫死，要改就重跑 `scripts/reparse.ts`。** 否決。`reparse` 是
  一支拿 `service_role` key 跑的維運腳本（`AGENTS.md`：service_role key 絕不可出現在
  `apps/web/`），使用者碰不到它。這等於把「我綁錯名字了」變成一張要開給維護者的工單，
  而在一個無法驗證帳號擁有權的系統裡，這件事會反覆發生。
- **不存歸屬欄位，每次讀取時即時推導。** 否決。統計層是對 `battles` 直接下條件與分組
  （`my_side is not null`、按 `team_signature` 分組、按日期切範圍），把歸屬變成讀取時
  才算的東西，等於要把那些條件搬進瀏覽器，並且一律讀回全部資料列與 `details`。
  這與「分頁讀取、不靜默截斷」的既有做法直接衝突。
- **只重跑目前沒有歸屬的列。** 否決。快，但修不好「已歸給 p2、應該翻成 p1」那一類，
  而那正是最需要被修好的一類 —— 使用者先綁了對手的名字，再綁自己的。
