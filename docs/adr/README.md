# 架構決策紀錄（ADR）

一張 ADR 記一個決定：**當時的處境、決定了什麼、後果是什麼**。它不是設計文件的替代品
—— `docs/specs/` 記的是動工前的整體設計，ADR 記的是**實作過程中撞出來、而理由不在
程式碼裡**的決定。

`docs/agents/domain.md` 要求 agent 探索前先讀這個目錄。

## 什麼該寫成 ADR

三個條件**同時**成立才寫：

1. **跨越單張票** —— 影響範圍不只這次改動
2. **未來會有人想推翻** —— 而且推翻看起來很合理
3. **理由不在程式碼裡** —— 讀 code 看不出來為什麼

三條全中的例子：`vue-shims.d.ts`（看起來像該刪的殘留，刪了會壞）。
一條都不中的例子：CSS 選擇器從 `#app` 改成 `#__nuxt`（讀 code 就懂，沒人會想改回去）。

寧可少寫。每張票做完問一次「有沒有跨票的決定」，沒有就沒有。

## 格式

檔名 `NNNN-kebab-case-title.md`，編號遞增不重用。

段落：狀態 / 日期 / 相關 → 脈絡 → 決定 → 後果 → 替代方案。
若這個決定特別容易被誤推翻，加一段「為什麼不推翻」或「為什麼不刪掉」，直接對著未來
那個想動手的人講話。

**主張要附證據。** 寫「實測 X」就要寫出量到什麼（指令、輸出、exit code）。分不清
「我量到的」和「我以為的」，這份紀錄的價值就沒了。

## 狀態

- `Accepted` —— 現行有效
- `Superseded by ADR-NNNN` —— 被後續決定取代。**不要刪除舊檔**，被推翻的理由本身
  就是有用的紀錄
