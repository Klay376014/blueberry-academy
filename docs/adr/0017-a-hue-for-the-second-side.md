# ADR-0017：第二側拿到第三支色相，而顏色不再是唯一通道

- 狀態：Accepted
- 日期：2026-09-07
- 相關：#144；前置 #143（側別的單一來源）；後續 #145（場面列與表頭沿用）

## 脈絡

`tailwind.css` 的註解一直寫著「見 `docs/adr/0010-two-palettes.md`」，**那個檔案從來不存在**
（`docs/adr/` 底下的 0010 是 `unovis-for-charts`）。雙色盤的原則因此沒有任何地方記載，
而這張票要做的事正是突破它——先把前提補上。

### 前提：兩套色盤，各自刻意單色

- **Uniform（淺色，SV 制服）** —— 白底、深藍資料、一支紅橘當例外。
- **Indigo Disk（深色，標題美術）** —— 深藍底、切面高光、亮青。預設是這一套（見
  `nuxt.config.ts`）。

共同原則是**單色加一個例外**：資料一律是那支藍的深淺，`--destructive` 那支紅橘專門留給
「錯誤／傷害／該注意的例外」。`--unfiled`（沒有完整選出的場次）刻意重用了 `destructive`
的值，正是這條原則的體現——寧可跟例外色共用，也不新增色相。

### 撞出來的問題

戰鬥時間軸用這兩支色票分辨對戰的兩側：第一側（有我的場次是我方）`--primary`，第二側
`--foreground`。回報是兩套主題下都看不出是哪一方在行動。

**量的方法。** 色票值讀自 `tailwind.css`，用 Oklab 歐氏距離（ΔE）當感知距離，二色覺用
Viénot / Brettel / Mollon (1999) 的模擬矩陣、在線性 RGB 內套用。以下所有數字皆由此法算出。

先量色票本身，也就是那條 2px 軌線的顏色：

| 主題        | 配對                         | 正常色覺 | 綠色盲 | 紅色盲 |
| ----------- | ---------------------------- | -------- | ------ | ------ |
| Uniform     | primary / foreground（現況） | 0.138    | 0.120  | 0.144  |
| Indigo Disk | primary / foreground（現況） | 0.288    | 0.388  | 0.246  |

**這張表解釋不了深色主題的回報**——0.288 不算近。所以量錯了東西：軌線只有 2px，而每一行
真正大面積著色的是底色，它疊在 `card` 上之後才是讀者看到的那個像素。改量composite 後的
底色：

| 主題        | 配對                                | 正常色覺   | 綠色盲     | 紅色盲 |
| ----------- | ----------------------------------- | ---------- | ---------- | ------ |
| Uniform     | primary 10% / foreground 5%（現況） | **0.0256** | 0.0292     | 0.0240 |
| Indigo Disk | primary 10% / foreground 5%（現況） | **0.0129** | **0.0120** | 0.0130 |

深色主題的兩側底色差 0.0129，綠色盲下 0.0120 —— 以 Oklab 的尺度而言那是**兩個幾乎相同的
像素**。回報說的就是這個。淺色 0.0256 也僅是勉強。

單色原則在這裡失效的原因是結構性的：它假設畫面上的東西**只需要跟背景分開**，而兩側需要
的是**彼此分開**。同一支色相的深淺可以把資料從紙上分出來，分不出兩個對等的東西。

## 決定

### 一、第二側拿一支自己的色相 `--side-second`

```
Uniform（淺色）    oklch(0.52 0.13 75)
Indigo Disk（深色） oklch(0.78 0.13 82)
```

金色，兩側底色濃度同時拉成相等的 12%。量出來的結果：

| 主題        | 配對                                    | 正常色覺 | 綠色盲     | 紅色盲 |
| ----------- | --------------------------------------- | -------- | ---------- | ------ |
| Uniform     | primary 12% / side-second 12%（本 ADR） | 0.0311   | 0.0418     | 0.0263 |
| Indigo Disk | primary 12% / side-second 12%（本 ADR） | 0.0323   | **0.0472** | 0.0265 |

深色主題的底色差從 0.0129 → 0.0323（2.5 倍），綠色盲下 0.0120 → 0.0472（3.9 倍）。淺色
主題 0.0256 → 0.0311。

選金色而非其他色相的理由，以及**它沒有解決的事**：

1. **藍↔金撐得住二色覺。** 上表綠色盲一欄是三組數字裡最大的（0.0418 / 0.0472）——藍黃軸
   是紅綠色盲保留的那一軸，所以模擬後距離不掉反升。兩支藍不具這個性質。
2. **不重用 `destructive`，理由是語意而非距離。** 誠實說：`side-second` 與 `destructive`
   的色票距離只有 0.117（淺）／0.171（深），並不遠。不重用是因為 `destructive` 在時間軸上
   已經是傷害數字與 `brn` 的顏色，第二側整片染成同色會讀成「出事了」。
3. **軌線層面在深色主題並沒有變好。** 色票距離 0.288 → 0.269，紅色盲下 0.246 → 0.226，
   都是略降。改善全部發生在底色，而底色才是大面積的那個通道。這是這個決定的已知邊界。

`--side-second` 的對應面沒有 `--side-first`：第一側就是這個 app 自己的 `--primary`，
「讀者自己那一側是主色」本身就是想要的意思。

### 二、顏色不再是唯一通道

上表也說明了為什麼換色相不夠：改善後的底色距離仍只有 0.03 上下。所以第二側的軌線同時
改成**虛線**，每一行再加一枚**說出側別的文字標記**（有我的場次是 `You` / `Opp`，旁觀
場次是 `P1` / `P2`，後者是 Showdown 的識別碼、不翻譯，見 ADR-0016）。三條通道任一失效，
另外兩條還在。

這不是新標準，是補上一條**這個 repo 早就對自己立過、但時間軸沒守的**標準——
`bg-unfiled-hatch` 的註解寫著「差異必須在灰階截圖和色盲讀者身上都活得下來」，它自己就是
同時上了顏色與斜線。

### 三、單色原則的邊界寫下來

`--side-second` **只用於對戰的兩側**，不是一支通用的第二強調色。除了兩側之外的任何東西要
用它，都應該先回來改這份 ADR。

## 後果

- 色盤從「單色 + 一個例外」變成「單色 + 一個例外 + 一支兩側專用色」。第三支色相存在的
  事實會誘使後人拿它當通用強調色，所以上面第三節把邊界寫死。
- 時間軸每一行多一欄 30px 的排水槽放側別標記，行寬相應變窄。
- 抽屜裡講到側別的地方必須同時換色，否則同一個面板會對「哪一側是哪個顏色」給出兩個
  答案。事件行與場面列因此在同一張票裡改完，抽屜表頭留給 #145。
- 側別標記是 9px 文字。金色對 `card` 的 WCAG 對比是 5.61:1（淺）與 7.80:1（深），過 AA
  的 4.5:1；但 9px 本身很小，**若日後回報看不清，該動的是字級而不是顏色**。
- 灰階不變量有測試（`side-encoding.spec.ts`）。它斷言的是「抽掉色相之後，兩側**剩下的
  差異恰好是虛線與實線**」，而不是「還有某種差異」——後者在新色相以 arbitrary value
  之類無法辨識的形式進來時會悄悄變成恆真，守門的測試會在全綠的狀態下死掉。

## 替代方案

**只把 `--foreground` 換成別的既有色票（例如 `chart-2`）。** 淺色的 `chart-2` 是
`oklch(0.541 0.123 257.2)`——還是同一個藍族，色相 257 對 262.7。這條路在淺色主題下等於
沒改。

**只加大兩側的明度／不透明度落差。** 這正是現況在做的事（10% 對 5%），而它是回報的問題
本身。加大落差只會讓其中一側讀成「另一側的淡化版」，而不是讀成對等的另一方。

**不換色，只加文字標記。** 可行，灰階下就夠了。沒選是因為它把「哪一方」從一眼可掃的
前注意通道降級成逐行閱讀——時間軸的存在理由是一眼讀完一場對戰（設計文件 §1）。

**改用版面分邊（第二側縮排靠右）。** 位置是最強的通道，灰階與色盲全過。沒選是因為
doubles 一行常帶兩三個目標與傷害數字，縮排會讓長訊息一直換行、行密度掉太多。若日後行寬
問題比辨識問題更痛，這是最該回來重新評估的一條。
