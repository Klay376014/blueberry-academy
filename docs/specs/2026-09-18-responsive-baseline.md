## 1. 目標

讓「這個畫面在手機上對不對」變成一個**有標準答案的問題**。

現況不是沒做，而是**沒有共同語彙**：`app/` 底下 70 個元件，只有 9 個出現過任何
breakpoint 前綴，其中 5 個只出現一次。已經做過的手機處理都是點狀的、各自為政的 ——
使用者選單把位址從按鈕移進選單（#192）、抽屜表頭把勝負標記移到下一列因為標題會截斷、
隊伍詳細頁在手機用上／下一隊取代左側清單。三個決定都是對的，但沒有一個寫在別人找得到
的地方，所以第四個人遇到同類問題時只能重新發明。

這份文件要交付的就是那份共同語彙：**驗收寬度**、**斷點語彙**、**觸控下限**、
**字級下限**，以及一件同樣重要的事 —— **哪些條件根本無法自動驗證**。

### 明確不做的事

**不引入瀏覽器層測試。** 見 §6：那是一個比這份基準大得多的決定，而它不是手機跑版的
必要條件。

**不改設計語言。** 這份文件不動色彩、不動字體、不動間距刻度，只回答「同一個設計在窄
寬度下怎麼站住」。

**不定義平板專屬版型。** 平板是「介於兩者之間的寬度」，不是第三套介面。§3 說明為什麼。

## 2. 硬點

1. **Tailwind v4 的預設斷點就是本專案的斷點。** `tailwind.css` 沒有覆寫 `--breakpoint-*`，
   所以 `sm` = 40rem（640px）、`md` = 48rem（768px）、`lg` = 64rem（1024px）。
   **不要新增自訂斷點** —— 多一個斷點就多一組沒人記得住的寬度，而下面的驗收寬度已經
   能表達所有要說的話。

2. **`768` 恰好落在 `md` 的邊界上。** 平板直立正好是 `md:` 開始生效的那一點，不是它
   之前。檢查 767 與 768 是兩個不同的畫面。

3. **觸控下限在 repo 裡已經存在，只是沒人宣告它。** `min-h-11`（44px）出現在六處：
   站台導覽連結、品牌連結、主題切換、語言切換、使用者選單、公開外殼的登入按鈕。
   這份文件不發明新數字，只是把既成事實變成規範。

4. **`apps/web` 沒有瀏覽器層測試。** 測試是 vitest + `@vue/test-utils`，跑在 jsdom 上，
   而 **jsdom 沒有排版引擎** —— 它不算寬度、不算換行、不知道什麼叫溢出。這不是設施
   的缺陷，是它本來就不做那件事。§6 因此把驗證拆成兩半。

5. **這個 app 的資訊密度是刻意的。** 時間軸的 9–10px 籤、對戰列的六隻圖示、統計格的
   等寬數字，都是設計文件裡論證過的取捨。基準**不能**用「全部放大到 16px」這種一刀切
   的規則去推翻它們，否則就是用無障礙當藉口拆掉產品本身（§5）。

## 3. 驗收寬度

六個寬度。每一個代表一件會壞的事，不是代表一台機器。

| 寬度 | 代表什麼                                           | 這裡會壞的是                                                     |
| ---- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 320  | 最窄的現役手機（iPhone SE 直立、開了大字級的裝置） | 寫死的像素寬度。六隻 48px 圖示是 288px，扣掉外殼與卡片內距就爆了 |
| 375  | 最常見的手機直立寬度                               | 一行塞三種資訊的列版型                                           |
| 414  | 大尺寸手機直立                                     | 「在 375 剛好」與「真的有餘裕」的差別                            |
| 768  | 平板直立，也是 `md:` 生效的第一點                  | 只有 `lg:` 的兩欄版型 —— 這一段常常是一欄內容配大片留白          |
| 1024 | 平板橫置 / 小筆電，`lg:` 生效的第一點              | 欄數切換的合理性                                                 |
| 1440 | 桌機                                               | 外殼 `max-w-[1280px]` 之外的留白                                 |

**平板不是第三套介面。** 768 與 1024 要檢查的不是「有沒有平板版」，而是「手機版與桌機版
之間的切換點放對了沒有」。目前最典型的錯放是隊伍詳細頁：兩欄要到 `lg` 才出現，於是
768–1023 這整段是一欄內容加半個螢幕的空白。

## 4. 斷點語彙

兩種做法，各有它對的場合。混用不是問題，**沒有理由地混用**才是。

**讓容器自己換行**（`flex-wrap`、`grid` 的 `auto-fit`、`min-w-0` + `truncate`）——
當「什麼時候該換行」取決於**內容**而不是螢幕時用它。一列標籤、一組籤、一行麵包屑，
它們的斷點是「東西放不下了」，而那個寬度隨語言、隨使用者名稱長度、隨隊伍數量而變。
寫死 `md:` 只會讓它在某個語言下提早或太晚換行。

**用 `sm:` / `md:` / `lg:` 前綴** —— 當**版型本身**要換一種說法時用它。一欄變兩欄、
側欄出現、清單變表格、導覽收進選單。這些不是「擠不下」，是「在這個寬度我們要講另一個
版本的故事」。

一個具體的反例，因為它現在就在 repo 裡：站台頁首靠 `flex-wrap` 把品牌、三個導覽連結、
主題切換、使用者選單折成多行。那不是內容驅動的換行，那是版型該換說法的地方 ——
它需要的是前綴，不是 wrap。

**一律手機優先。** 無前綴的那組類別是手機的樣子，前綴只做加法。不要用 `max-*` 方向的
變體來補救桌機優先的寫法。

## 5. 下限

### 觸控目標：44px

可按的東西**最小 44×44 CSS px**（`min-h-11` / `min-w-11`），相鄰兩個之間至少 8px
（`gap-2`）。

為什麼是 44 而不是 WCAG 2.5.8 的 24：24 是**不會被判違規**的下限，44 是 iOS 的建議值
（Android 是 48dp）。這個 app 的使用者是在手機上看自己天梯戰績的人，他們的姿勢是單手、
拇指、走路。取 44。

**視覺尺寸與可按尺寸是兩件事。** 提示按鈕畫成 16px 的圓圈是對的 —— 它不該搶走隊伍旁邊
的注意力。要改的是它的**命中範圍**，不是它的直徑。用內距或 `::before` 把命中區撐到 44，
讓圖形維持原樣。這條規則讓 §2.5 的密度與這條下限可以同時成立。

### 字級

- **句子** ≥ 16px（`text-base`）。整段說明、空狀態的話、錯誤訊息。
- **次要句子** ≥ 14px（`text-sm`）。附註、表單標籤。
- **標記** 可以更小。籤、側別標、狀態縮寫、等寬數字 —— 它們不是句子，是**符號**，
  而符號的可讀性來自對比與位置，不是字級。

界線就是「這是一句話嗎」。一句用 10px 寫的話是排版錯誤；一個用 10px 寫的 `TOX` 不是。

但標記有它自己的義務：**它不能是某個資訊唯一的管道，除非它有無障礙名稱。** 時間軸的
側別籤之所以存在，正是因為色彩在灰階或色盲下會失效（ADR-0017）—— 同一個道理，籤在
10px 下對某些讀者也會失效，所以它指涉的東西必須在別處也說得出來。

## 6. 驗證方式，以及它的極限

**分成兩半，因為設施只支援其中一半。**

### 自動驗的：class 契約

`test/nuxt/responsive.spec.ts` 斷言的是**元件有沒有帶著約定的類別** —— 外殼的水平內距
是不是兩段式、高度是不是 `dvh`、頁首與頁尾裡每一個可按元素是不是帶著 `min-h-11`。

這比真正的驗證弱得多：它證明的是「有人寫了那個類別」，不是「畫面沒有壞」。一個帶著
`min-h-11` 卻被父層裁掉的按鈕，這支測試看不出來。

它的價值在**防回頭**：這些下限是一次一次手動修出來的，沒有測試的話，下一個人刪掉一個
`min-h-11` 不會有任何東西攔他。後續每一張 RWD 票都應該把自己那頁的契約加進這支 spec。

### 只能人工驗的：版面本身

**是否橫向捲動、是否重疊、是否截斷到讀不懂、換行後的閱讀順序對不對** —— 這四件事需要
排版引擎，而 jsdom 沒有。**這些一律在瀏覽器裡、在 §3 的六個寬度逐一看過**，並把看過
的結果寫回票上。

為什麼不裝 Playwright：那是要養一整套瀏覽器測試設施的決定，牽涉 CI 時間、Supabase 的
測試資料、與現有 vitest 套件的邊界，值不值得應該由它自己那張票來論證，而不是夾帶在一份
基準文件裡通過。目前的規模（八個頁面、一個人）人工掃一遍是便宜的。**如果哪天 RWD 回歸
開始重複發生，那就是重開這個決定的訊號** —— 而重複發生這件事，靠的就是把人工掃描的結果
寫回票上才看得見。

## 7. 後果

- 後續每一張 RWD 票的驗收條件，都應該分成「class 契約（自動）」與「六個寬度人工掃描」
  兩段，而不是寫一句「在手機上要好看」。
- `min-h-11` 從六個巧合變成規範。新增任何可按元素時，它是預設值而不是額外工作。
- 新增自訂斷點需要理由。目前沒有任何一個場景需要。
- 這份基準不涵蓋**列印**與**極端縮放**（400% zoom）。兩者都是真的議題，也都不是這次
  要解決的問題。

## 8. 替代方案

**只寫進 AGENTS.md 的實作守則。** 守則是給「怎麼寫」的一行行規則，這裡有一半的篇幅在
論證取捨（為什麼是 44、為什麼標記可以小於 16、為什麼不裝 Playwright）。論述放守則會把
守則稀釋成讀不完的東西。守則裡該有的是一行指標，指向這裡。

**直接裝 Playwright 然後斷言 `document.body.scrollWidth`。** 這會是真的驗證，而不是
class 契約。否決的理由不是技術上不好，而是它把一個獨立的基礎設施決定夾帶進來 —— 見 §6。
