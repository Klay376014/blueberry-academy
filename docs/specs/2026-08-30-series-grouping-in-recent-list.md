## 1. 目標

讓「最近對戰」清單看得出**哪幾場屬於同一個 series**。

現況：連續對上同一位玩家時，一個 BO3 的三場 game 與三場各自獨立的天梯對戰在清單上
長得完全一樣 —— 同一個名字、同一天、三列。使用者得自己從回合數與選出去猜哪幾場是同
一個系列打的，而那正好是猜不出來的東西（同一個對手一天內打好幾個系列是常態）。

CONTEXT.md 已經把這件事定義完畢：series 是 Bo3 下 2–3 個 game 構成的單位，
`battles.series_id` 存 Showdown 的母對戰 id。這份文件只處理**清單怎麼把它畫出來**。

### 明確不做的事

**不改變儲存的單位。** 系統永遠以 game 為單位儲存（CONTEXT.md）。這份設計動的是
**呈現與計算的單位**，不動 schema，也不新增任何查詢 —— `battleStats.ts` 的
`asGames` / `asSeries` 兩條路徑都留著，改的只是「誰來決定走哪一條」（§4）。

**不宣稱系列的勝者。** 清單只數卡片裡看得到的勝敗場數，理由見 §3「卡頭放什麼」。

**不做跨頁的系列補齊。** 清單有邊界，系列可能被邊界切斷。以 series 計的 `LIMIT`
（§4）讓 Bo3 的邊界落在系列之間而不是系列中間，但篩選器與匯入進度仍可能讓一個系列
只剩一場在畫面上。卡片呈現的永遠是「這個清單裡看得到的那幾場」，不會為了補完而多打
一次 API。

## 2. 硬點

1. **資料已經在手上。** `RecentBattle.seriesId` 已經從 `battles.series_id` 讀進清單
   （`useRecentBattles.ts`），抽屜也已經用 `gamesOfSeries()` 在同系列的 game 之間
   切換。這個功能不需要新的查詢、不需要改 schema。

2. **log 不說這是第幾局。** `|uhtml|bestof|` 只帶母對戰 id 與下一場的連結
   （`packages/replay-parser/src/replay.ts`），沒有局次欄位。所以「第 1 / 2 / 3 局」
   一律是**由 `played_at` 遞增推導出來的序號**。抽屜的系列切換器已經是這樣做的
   （`BattleDrawer.vue` 用 `index + 1` 配 `battle.drawer.game`），清單沿用同一套，
   兩處才不會對同一場 game 講出不同的局次。

3. **推導出來的局次在「系列不完整」時會說謊。** 只匯入了第 2、3 場時，它們會被編成
   第 1、2 局。這是接受的取捨：真實局次無從得知，而「清單裡的第幾場」至少是使用者
   眼前看得到的事實。

   但兩處的「不完整」不是同一件事：**抽屜的切換器讀的是資料庫裡整個系列**
   （`gamesOfSeries()`），清單讀的是畫面上那幾場。所以清單只要少拿到系列的其中一場，
   同一個 replay 就會在卡片上叫第 1 局、在它打開的抽屜裡叫第 2 局。清單的 `LIMIT`
   因此不切在系列中間（實作於 `useRecentBattles`：最後一場若屬於某個系列，把該系列
   剩下的場次一併納入，那些列本來就在記憶體裡）。**日期篩選器仍可能切斷一個系列**
   —— 那種情況下抽屜知道得比清單多，而清單沒有辦法知道自己少了什麼。

4. **Bo3 的分數變化似乎只記在決勝的那一場。** 使用者提供的畫面裡，同一個系列的三場
   只有最新的一場帶 `+26`，另外兩場沒有任何 rating。fixture 無法佐證這點 ——
   `packages/replay-parser/test/fixtures/` 的兩份 Bo3 都是**沒有 rating 的比賽場**
   （`gen9championsvgc2026regmbbo3-*`）。因此設計不建立在這個猜測上：卡頭顯示的是
   **卡片內非 null 的 `ratingDelta` 總和**，無論 Showdown 記在一場還是三場都對。

5. **天梯 Bo1 的 `series_id` 是 null。** 每一列自成一個單位。**不可以**因為對手與
   日期相同就把它們併起來 —— 那正是這個功能要區分的兩件事。

## 3. 設計

選定的畫法是**系列卡片**（四個方案的比較與取捨見 §8）：同系列的 game 收進一張卡，
卡頭把整個系列的共通資訊講完，內部的 game 列只留下彼此不同的部分。

```
┌── XwingVGC   2–1   BO3   2026/8/18            +26 ──┐
│  第1局   勝   [選出] vs [選出]              15 回合  │
│  第2局   勝   [選出] vs [選出]               9 回合  │
│  第3局   敗   [選出] vs [選出]               3 回合  │
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│  勝   MoonlightSun  2026/8/17 · 天梯 · 12 回合   +18 │
│       [選出] vs [選出]                               │
└──────────────────────────────────────────────────────┘
```

### 分組規則：清單順序上的連續段

以清單**目前的順序**掃過一遍，把 `seriesId` 相同且**相鄰**的 game 收成一組。

不重排、不跨越中間的其他對戰。清單依 `played_at` 排序，同一個系列本來就連著；篩選器
拿掉其中一場時，剩下的仍然相鄰，仍是同一張卡。這條規則讓「畫面上的順序」是唯一的
事實來源，不會出現卡片內容與清單排序打架的狀況。

`seriesId` 為 null 的 game 永遠自成一組，即使相鄰。

### 一場的系列不畫成卡片

一組只有一個 game 時（天梯 Bo1，或系列的其他場被篩掉、還沒匯入、落在 20 筆之外），
畫成現在的一般列。**理由**：一張只裝一場的卡片，卡頭與唯一的列講同一件事，讀者會以為
「這個系列只有一場」—— 而那件事我們並不知道。

### 卡頭放什麼

| 欄位     | 來源                             | 缺值時                               |
| -------- | -------------------------------- | ------------------------------------ |
| 對手     | 組內任一場的 `opponentUsername`  | 沿用 `battle.drawer.unknownOpponent` |
| 比分     | 組內 `result` 的勝場數–敗場數    | `result` 為 null 的場次不計入任一邊  |
| 賽制     | `bestOfLabel(formatId)`          | 同現況                               |
| 日期     | 組內最早一場的 `playedAt`        | —                                    |
| 分數變化 | 組內非 null `ratingDelta` 的總和 | 全部為 null 時整個不顯示             |

比分寫成 `2–1`，**不加上「勝」或「敗」的結論**。清單看到的可能是一個還沒打完、或還
沒匯入完的系列，`2–1` 是事實，「你贏了這個系列」不是。

平手（`result === 'tie'`）不計入任一邊，理由與 `result` 為 null 相同：比分是兩個
數字，硬把第三種結果塞進去會讓 `2–1` 這種寫法變得不可信。

### game 列留下什麼

去掉對手名字與日期（卡頭講過了），保留：局次徽章、勝負、雙方選出、回合數。
每一列仍然各自可以點開抽屜，`data-testid="recent-battle"` 不變 —— 抽屜是以
`replayId` 開的，卡片不改變這件事。

**卡頭本身不可點。** 它旁邊就是三個各自可點的 game 列，再讓卡頭也可點，「點它會開哪
一場」沒有好答案。系列層級的巡覽已經在抽屜裡了（`BattleDrawer` 的系列切換器）。

### 計數與 `LIMIT` 跟著計算單位走

Bo1 的格式下清單數 game、取 20 個 game；Bo3 的格式下清單數 series、取 20 個
series。單位由選定的 format 決定，理由與規則見 §4。

## 4. 計算單位不再是一個選項

現況：篩選器上有一組「計算單位 每局／每系列」的切換（`FilterBar.vue`，
`StatsFilters.aggregate`），預設每局。**移除它，改由 format 決定。**

### 規則

```
bestOfLabel(formatId) === 'BO1'   → 以 game 為單位
BO2 / BO3                          → 以 series 為單位
```

沒有第三種情況，也沒有使用者可以選的餘地。

### 為什麼這是對的

**format 已經把答案講完了。** 篩選器的 format 是**單一且必選**的 `format_id`
（`useStatsFilters.ts` 的註解說明了為什麼不能是「全部格式」），而 CONTEXT.md 定義
Bo1 的天梯格式與它的 Bo3 對應格式是**不同的格式**。所以只要選定了 format，這批
資料是 Bo1 還是 Bo3 就沒有懸念 —— 再問使用者一次「你要用哪個單位看」，是把一個
已知的答案當成選項。

**兩個組合本來就沒有意義。** Bo1 格式下「每系列」和「每局」的結果完全相同（每個
`series_id` 都是 null，每一場自成一個系列，`asSeries` 的註解已經寫明了這點）——
那個切換在 Bo1 下是個什麼都不會發生的按鈕。而 Bo3 格式下「每局」會把一個 2–1 的
系列算成 2 勝 1 敗，勝率因此被單場的輸贏稀釋 —— Bo3 的勝負本來就是以系列計的。

**少一個要解釋的東西。** 「計算單位」這四個字要讀者先知道 game 與 series 的差別、
再知道自己現在在看哪一種格式，才決定得了。移掉它，這個知識就從使用者身上移到程式裡。

### 連帶要改的

- `StatsFilters.aggregate` 與 `defaultStatsFilters()` 的 `aggregate: 'game'` 移除；
  `useStats` 改為由 `filters.formatId` 推導單位傳給 `resultUnits` / `overallTally`
  / `teamStats`。`battleStats.ts` 的 `Aggregate` 型別與兩條聚合路徑**都留著**，
  它們沒有錯，錯的只是由誰決定。
- `FilterBar.vue` 移除那組 fieldset；i18n 移除 `filters.aggregate` / `filters.byGame`
  / `filters.bySeries`。
- **摘要的「場數」要跟著單位走。** `summary.games`（「場數」）在 Bo3 下數的是系列，
  所以要有 series 版本，由推導出來的單位挑。
  **連續紀錄不跟。** `TrendSection` 寫死 `resultUnits(battles, 'game')` 並在註解說明
  了原因：「三連勝」講的是最後打的三場，把一個 Bo3 折成一個單位會讓三場悄悄變成一場。
  它的文案「連勝，以每局計」因此是準確的 —— 而且在其他數字改用系列之後更該留著，
  它是畫面上唯一標明自己用哪個單位的地方。
- 「最近對戰」的 `LIMIT`：Bo1 取 20 個 game，Bo3 取 **20 個 series**（由新到舊累積
  到第 20 個不同的 `series_id` 為止，該系列的 game 全數納入）。清單標題旁的計數
  跟著顯示同一個單位的數量。

### 取捨

一個 Bo3 帳號從此看不到「以單場計」的勝率。這是刻意的：那個數字回答的問題
（「我單場的勝率」）在 Bo3 的賽制下不是使用者實際在比的東西，而想看單場表現的人
仍然看得到每一場 —— 清單裡的每個 game 列都在，只是被收在系列卡片裡。

## 5. i18n

新增三個 key（`en.json` / `zh-TW.json`）：

- `battle.recent.seriesScore` — `{wins}–{losses}`（純數字，兩個語系相同）
- `battle.recent.seriesLabel` — 卡片的群組標籤，給螢幕閱讀器：`與 {opponent} 的 {count} 場系列賽`
- 局次沿用既有的 `battle.drawer.game`（`第 {number} 局`），不另開 key —— 同一個概念
  在兩個地方必須是同一句話。

移除三個 key：`filters.aggregate`、`filters.byGame`、`filters.bySeries`（§4）。

單位會變的每個標籤都要有 series 版本，由推導出來的單位擇一：

| game 版本                          | series 版本                                    | 用在           |
| ---------------------------------- | ---------------------------------------------- | -------------- |
| `summary.games`（場數）            | `summary.series`（系列數）                     | 摘要第一張卡   |
| `teams.sample`（{games} 場）       | `teams.sampleSeries`（{games} 系列）           | 隊伍卡的樣本數 |
| `teams.games`（場數）              | `teams.seriesCount`（系列數）                  | 隊伍詳情       |
| `trend.windowOf` / `trend.winRate` | `trend.windowOfSeries` / `trend.winRateSeries` | 走勢圖的視窗   |

**不跟著變的**：`teams.sample` 用在選出（bring）上的那一處、`teams.segment`、
`teams.unfiledShort` —— 選出永遠以 game 計（Bo3 每一局選出不同，沒有系列層級的選出），
所以那些「場」是準確的。`summary.streakWins` / `streakLosses` 同理，理由見 §4。

對手名字、format 標籤照現況不進翻譯檔。

## 6. 無障礙

- 卡片是 `role="group"` 加 `aria-label`（`seriesLabel`），讀者才知道接下來三個按鈕
  屬於同一個系列。
- 局次徽章不是唯一的訊號：卡片有邊框、卡頭有比分，靠顏色分不出來的人也讀得到分組。
- 卡片本身不可聚焦，Tab 順序仍然是一場 game 一站。

## 7. 測試策略

**分組邏輯是純函式**（`groupIntoSeries(recent: RecentBattle[]): RecentGroup[]`），
放在 `features/stats/utils/`，與元件分開測：

- 三場同 `seriesId` 相鄰 → 一組
- `seriesId` 為 null 的連續三場、同對手同日期 → 三組（**這條是這個功能的核心**）
- 中間夾著別的對戰的同 `seriesId` → 兩組，且不重排
- 只有一場的系列 → 一組，且被標記為不畫卡片
- 比分：`result` 為 null 與 `tie` 都不計入任一邊
- 分數變化：全 null → null；部分 null → 只加非 null 的

**元件測試**（`test/nuxt/`）：卡片渲染出三個 `recent-battle` 按鈕、卡頭出現一次
對手名字、單場的系列不畫卡片、點 game 列仍然開對應的抽屜。

**計算單位的推導**（§4）另外測：

- `bestOfLabel` 的三種輸出各自對到的單位（BO1 → game，BO2 / BO3 → series）
- 換 format 就換單位：同一批資料在 Bo1 與 Bo3 格式下的總勝率不同，且 Bo3 的那個
  與舊的「每系列」切換算出來的相同
- Bo3 下的 `LIMIT` 取的是 20 個 series，且第 20 個系列的 game **全數**在畫面上
  （不會切在系列中間）
- 篩選器上不再有 `filter-by-game` / `filter-by-series` 這兩個 testid

## 8. 決策紀錄

**為什麼不是「系列收合成一列」。** 收合能讓一屏看到更多對手，但清單被掃視的理由是
「我上次對這支隊帶了什麼」（`RecentList` 的檔頭註解），而收合起來的那一列放不下三場
各自的選出 —— 那正是要看的東西。

**為什麼不是「只加徽章與底色」。** 改動最小，但底色是最弱的分組訊號：兩個系列相鄰時
要靠深淺交替才分得開，深色主題（Indigo Disk）下更難拉開差距，而系列比分仍然要自己數。

**為什麼不是「左緣括號」。** 它保留了均質的清單，代價是縱線在長清單裡邊界感弱，而且
對手名字與日期仍然重複三次 —— 卡片順手解決了那個重複。

**為什麼比分不宣稱勝者。** 見 §3。這與 CONTEXT.md 的立場一致：series 層級的勝負可以
從同 `series_id` 的 games 推導，但推導的前提是那些 games 都在手上。
